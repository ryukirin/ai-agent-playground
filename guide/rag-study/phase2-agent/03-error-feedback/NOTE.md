# 2-3. Error Feedback Loop（自己修復） — 学習ノート

## 概念

ツール実行が失敗した時、エラーメッセージをLLMに渡して修正策を生成し、再実行する。

```
execute ─── success ──→ END
    │
   error
    │
    └──→ analyze（LLMがエラーを分析・修正）──→ execute（再実行）
```

## 3種類のエラーパターンと対処

| エラー | 原因 | 対処 |
|---|---|---|
| **TimeoutError** | API応答が遅い | 同じ入力でリトライ。指数バックオフ |
| **ValidationError** | 入力フォーマットが不正 | エラーメッセージから修正方法を推測して入力を修正 |
| **RateLimitError** | API呼び出し制限 | 待機してからリトライ |

## LLMによるエラー分析の利点

- if-else でハードコードするより**未知のエラーにも対応できる**
- エラーメッセージから修正方法を「推測」できる
- 例: `'date' must be in YYYY-MM-DD format` → 自動でフォーマットを修正

## 設計上の重要ポイント

| ポイント | 理由 |
|---|---|
| 最大再試行回数を設定 | 無限ループ防止 |
| エラーの種類に応じた戦略切替 | タイムアウトはリトライ、バリデーションは修正 |
| 指数バックオフ | レート制限に対してはwait時間を徐々に延ばす |
| エラーログの保存 | 同じエラーを繰り返さないための学習 |

## Self-Reflection との違い

| | Self-Reflection (2-2) | Error Feedback (2-3) |
|---|---|---|
| 何を評価するか | **回答の品質** | **ツール実行の成否** |
| 失敗の種類 | 回答が不十分 | APIエラー、入力ミス |
| 修正方法 | 再検索・再生成 | エラーメッセージから入力を修正 |
| 両方組み合わせ | ツールが成功した後、回答品質も評価する |
