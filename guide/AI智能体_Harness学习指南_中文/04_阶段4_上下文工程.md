## 4-1. 讲解

### 何为上下文工程

> **设计「模型接收什么信息、如何结构化、何时进入上下文窗口」的学科。**

它不仅是 prompt,还包括记忆·工具·检索·状态在内的「整个信息环境」的设计。业界称其为「**定义 2026 年的技能**」。因为模型再聪明,若呈现的信息不当,就无法正确运作。

### 核心难题:Context Rot(上下文腐化)

最重要的概念。**上下文窗口越长,即便最前沿的模型性能也会下降**,这一现象称为 context rot。

为何发生:
- Transformer 在所有 token 之间计算 n²(两两)的关系。token 越多,这份「注意力(attention)」被摊得越薄。
- 模型在超长序列上的训练相对较少,处理远距离依赖的能力下降。

结论是,模型也有**有限的「注意力预算(attention budget)」**。和人类的工作记忆一样,塞太多信息反而会丢掉关键点。

### 核心原则

> **维持最小且高信号的 token 集合。** 即便模型在进化,也要把上下文当作稀缺的有限资源。

「以防万一全都放进去」是最糟的做法。噪声会稀释信号。

### 4 种实践技巧

**(1) Just-In-Time Retrieval(即时取用)**
不预先塞入全部数据,只让它持有轻量的「标识符(文件路径·ID)」,在需要时用工具动态取用。如同人只记文件名,需要时才打开文件。

**(2) Compaction(压缩)**
对话历史变长时进行总结。保留重要的设计决策·未解决的课题,丢弃冗余的工具输出。诀窍是「**先最大化 recall(不遗漏)→ 再提升 precision(去冗余)**」的顺序。

**(3) Structured Note-Taking(结构化笔记)**
让智能体把进展·决定事项·TODO 写到外部记忆文件。即便上下文被重置,只要重读这个文件就能保持一致性。长周期任务必备。

**(4) Sub-Agent(子智能体)**
把聚焦的任务委派给专门的子智能体,**只返回总结而非细节**。可让父智能体的上下文保持轻量,也能并行启动多个子智能体探索。

### 系统提示词与示例的 "Goldilocks zone"

- **系统提示词**:在死板硬编码(脆弱)与含糊指令(无效)之间取中。以「具体到能引导行为、又灵活到给出强启发式」的"高度(altitude)"来写。
- **示例(few-shot)**:与其穷举边界情况,不如**精选多样且有代表性(canonical)的示例**。「对 LLM 而言,一个示例胜过千言万语」。

### 业界的设计模式(Write / Select / Compress / Isolate)

上下文工程目前**还没有统一的「理论」**(2025 年年中才命名的新兴领域)。但在实务中反复复用的**设计模式已事实上被编目**。被引用最多的,是 LangChain / Cognition 总结的 **4 大策略**。

| 策略                | 含义                     | 与上面 4 种技巧的对应      |
| ------------------- | ------------------------ | -------------------------- |
| **Write(写到外部)** | 保存在上下文窗口**之外** | (3) Structured Note-Taking |
| **Select(选入)**    | 只把需要的引入窗口       | (1) Just-In-Time Retrieval |
| **Compress(压缩)**  | 只保留需要的 token       | (2) Compaction             |
| **Isolate(隔离)**   | 拆分上下文以防干扰       | (4) Sub-Agent              |

→ 本阶段的 4 种技巧并非偶然,而是**业界 4 大策略的缩影**。各策略的代表性具体模式:

- **Write**:Scratchpad(把计划退避到文件/状态)/ Long-term Memory(跨会话记忆)/ **Memory File(`CLAUDE.md` 即代表)**
- **Select**:RAG / JIT Retrieval / **Tool-RAG**(工具多时只提示相关工具)/ Hybrid Retrieval(grep + 向量 + re-rank)
- **Compress**:Summarization·Compaction(如 95% 时 auto-compact)/ Trimming·Pruning(移除旧历史)
- **Isolate**:Sub-agent / Multi-agent / Sandbox Offloading(把图像·大数据放到窗口外)/ State-field Isolation(用状态 schema 只暴露所需)

### 反模式 ── 上下文失败的 4 种模式

「全都塞进去」是最大的反模式。过长的上下文会以下列方式劣化性能(Drew Breunig 的分类):

| 失败模式                | 含义                            |
| ----------------------- | ------------------------------- |
| **Context Poisoning**   | 幻觉混入上下文,并向后续推理传播 |
| **Context Distraction** | 信息过多导致焦点模糊            |
| **Context Confusion**   | 无关细节混入回答                |
| **Context Clash**       | 相互矛盾的信息彼此干扰          |

> 小结:**统一理论尚未确立,但「原则 → 4 大策略 → 具体模式 → 反模式」这一分层的模式体系正在收敛**。实务中,与其「等理论」,不如「用这套正在收敛的模式」。

## 4-2. 示例代码 ── 按 token 量判断的 Compaction(经典模式)

「历史变长就总结并折叠」── 这是上下文工程中最著名的 **Compress 经典模式**。要点是:判断依据用**实际 token 量而非消息条数**,当超过窗口的某一比例(Claude Code 约 95%)时压缩。把它装进阶段 2 的调查智能体。

```python
from transformers import AutoTokenizer

MODEL          = "Qwen/Qwen2.5-72B-Instruct"
SUMMARIZER     = "Qwen/Qwen2.5-7B-Instruct"   # 总结用轻量模型,便宜
CONTEXT_WINDOW = 32768                         # 模型的最大上下文(示例)
COMPACT_AT     = 0.8                           # 使用率超过它就压缩(实战 ~0.95)

tokenizer = AutoTokenizer.from_pretrained(MODEL)

def count_tokens(messages):
    """数出聊天形式的实际 token 数(准确。简易可用 总字符数 ÷ 4 代替)"""
    return len(tokenizer.apply_chat_template(messages, tokenize=True))

def compact_history(messages):
    """把旧历史总结并折叠(= Compress)。最近的往来保留。"""
    keep, to_summarize = messages[-4:], messages[:-4]   # 保留最近2个来回
    if len(to_summarize) < 2:
        return messages
    summary = client.chat.completions.create(
        model=SUMMARIZER, max_tokens=1024,
        messages=[{"role": "user", "content":
            "请总结以下工作日志。必须保留重要的决定事项·已查明的事实·未解决的课题,"
            "丢弃冗余的工具输出。\n\n" + str(to_summarize)}],
    ).choices[0].message.content
    return [{"role": "user", "content": f"【至今为止的总结】\n{summary}"}] + keep

def run_agent_with_compaction(user_message, max_iterations=20):
    messages = [{"role": "user", "content": user_message}]
    for i in range(max_iterations):
        # ★ Compress: token 使用率超过阈值就压缩
        used = count_tokens(messages)
        if used > CONTEXT_WINDOW * COMPACT_AT:
            print(f"  📦 压缩(已用 {used} tok / 上限 {CONTEXT_WINDOW})")
            messages = compact_history(messages)

        resp = client.chat.completions.create(
            model=MODEL, max_tokens=2048, tools=TOOLS, messages=messages,
        )
        msg = resp.choices[0].message

        # 助手发言规范化为 dict 再入历史(为了计数 token & 更健壮)
        a = {"role": "assistant", "content": msg.content or ""}
        if msg.tool_calls:
            a["tool_calls"] = [
                {"id": tc.id, "type": "function",
                 "function": {"name": tc.function.name, "arguments": tc.function.arguments}}
                for tc in msg.tool_calls
            ]
        messages.append(a)

        if not msg.tool_calls:                 # 没调用工具就完成
            return msg.content
        for tc in msg.tool_calls:              # 以 tool 角色返回观察
            args = json.loads(tc.function.arguments)
            messages.append({"role": "tool", "tool_call_id": tc.id,
                             "content": run_tool(tc.function.name, args)})
```

> 📌 它之所以「经典」,在于 3 点:**① 用 token 量判断压缩 / ② 保留最近、只总结较旧部分 / ③ 总结用便宜的小模型**。在阶段 2 的朴素循环上仅加这一个机制,超过 100 轮的长调查也不会撑爆窗口(`client` / `TOOLS` / `run_tool` 沿用阶段 2)。

## 4-3. 练习

1. **【理解】** 用自己的话解释 context rot。「上下文越长越好」为何是错的?从 attention budget 角度说明。
2. **【实现】** 补全上面的 `run_agent_with_compaction`(填入阶段 2 的工具执行部分),在长对话中观察压缩触发的过程。比较压缩前后对话历史的长度变化。
3. **【设计】** 假设你要做「调查 100 个文件代码库的智能体」。分别就「预先把全部文件放进 context」与「JIT retrieval」两种方式,把 token 消耗·精度·延迟的权衡列成表。
4. **【进阶】** 实现 Structured Note-Taking。给智能体一个 `update_notes(text)` 工具,让它每步把进展写入文件。然后故意重置上下文(清空 messages),仅重读 notes 文件,试试能否继续作业。
5. **【设计模式】** 为 Write / Select / Compress / Isolate 4 大策略各配 1 个本指南出现过的具体例子。再就你当前参与的系统(例:本项目 `CLAUDE.md` 的运用)各举 1 个可能发生的 **4 种反模式(poisoning / distraction / confusion / clash)**,并说明用哪种策略来防范。
