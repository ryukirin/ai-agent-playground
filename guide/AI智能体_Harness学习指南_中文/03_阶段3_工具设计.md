## 3-1. 讲解

### 工具设计决定智能体的性能

阶段 2 中定义了工具,但**工具「描述文(description)」的质量**会极大左右智能体的聪明程度。Anthropic 称之为 **ACI(Agent-Computer Interface)**,强调「应投入与面向人类的 UI 设计(HCI)同等的精力」。

模型只能依靠工具的名字和描述来判断「何时用哪个工具」。描述含糊,模型就会选错工具、传错参数。

### 好工具设计的原则

**(1) 最少·不重叠(minimal, non-overlapping)**
工具要少,职责不要重叠。Anthropic 的名言:

> 「如果一位人类工程师都无法立刻说出该用哪个工具,那就别指望 AI 智能体能做得更好。」

`search`、`find`、`query` 这类相似工具并列时,模型会犹豫。

**(2) 清晰命名·充实描述**
工具名用「动词 + 宾语」具体化(`get_weather` 好,`data` 差)。描述要写明「做什么·何时用·参数含义·返回形态·边界情况」。

**(3) 命名空间(namespacing)**
工具多时用前缀分组。按服务分:`asana_search` / `jira_search`;按资源分:`asana_projects_search` / `asana_users_search`。边界清晰,模型易选。

**(4) 节省上下文的输出设计**
工具返回值过大会挤占上下文窗口(直接关联阶段 4 的 context rot)。与其全量返回,不如总结、分页、「只返回标识符、需要时再取详情」。

**(5) 可组合(composable)**
单个工具要小,能像零件一样组合进多样的工作流。

### 陷阱

- **工具数量过多**:重复·过量的工具会让模型混乱,诱导其走低效策略。
- **过度抽象**:比起花哨的高层工具,`bash`、`read_file` 这类基础零件往往让模型更灵活地解决问题(LangChain 也指出「给它计算环境、让模型自己设计解法」有时更好)。

## 3-2. 示例代码 ── 坏工具与好工具

```python
# ❌ 坏例:描述含糊、职责重叠、参数含义不明
BAD_TOOLS = [
    {"type": "function", "function": {"name": "data", "description": "处理数据",
     "parameters": {"type": "object", "properties": {"x": {"type": "string"}}}}},
    {"type": "function", "function": {"name": "get", "description": "获取",
     "parameters": {"type": "object", "properties": {"x": {"type": "string"}}}}},
]
# → 模型无法判断「该用 data 还是 get」。

# ✅ 好例:命名具体、描述充实、用命名空间整理(OpenAI 兼容 function 格式)
GOOD_TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "db_users_search",
            "description": (
                "按姓名或邮箱检索用户库,最多返回20条。"
                "为部分匹配而非完全匹配。无结果时返回空列表。"
                "需要单个用户的详情时请用 db_users_get。"
            ),
            "parameters": {
                "type": "object",
                "properties": {
                    "keyword": {"type": "string", "description": "姓名或邮箱的子串"},
                    "limit": {"type": "integer", "description": "最大条数(默认20,上限100)"},
                },
                "required": ["keyword"],
            },
        },
    },
    {
        "type": "function",
        "function": {
            "name": "db_users_get",
            "description": "指定用户ID,返回该用户1条的全部字段。不存在则返回错误字符串。",
            "parameters": {
                "type": "object",
                "properties": {"user_id": {"type": "string", "description": "用户的唯一ID"}},
                "required": ["user_id"],
            },
        },
    },
]
# → search(多条·部分匹配)与 get(单条·按ID)职责明确分离。
#   命名空间 db_users_* 边界也清晰。
```

### 节省上下文的例子(只返回标识符)

```python
def db_users_search(keyword, limit=20):
    rows = query_db(keyword, limit)
    # ❌ 返回全部字段会挤占上下文
    # return json.dumps(rows)  # 每个用户带地址·历史…体积巨大

    # ✅ 列表只返回「ID + 姓名」,详情用 get 按需获取(JIT retrieval)
    return json.dumps([{"id": r["id"], "name": r["name"]} for r in rows])
```

## 3-3. 练习

1. **【基础】** 把阶段 2 的 `list_files` 工具描述故意改成「处理文件」一个含糊的词,观察行为是否变化。再把「返回什么·参数含义·空目录时的行为」补进描述加以改善。
2. **【设计】** 设计一套「公司内文件检索智能体」的工具集(3~4 个)。如 `files_search`(按关键词列出)、`files_read`(按路径读全文)等,注意命名空间与职责分离,为每个工具写完整描述(做什么·何时用·参数·返回·边界)。
3. **【点评】** 指出以下工具集的 3 个问题并改善:`search`, `find`, `lookup`, `query`, `get_data`, `fetch`(全是「找数据」类且描述只有一个词)。
4. **【进阶】** 设想某工具返回值有 10,000 行,想出 3 种不挤占上下文的返回方式(分页 / 总结 / 仅返回标识符等)。分别说明各自的优缺点。
