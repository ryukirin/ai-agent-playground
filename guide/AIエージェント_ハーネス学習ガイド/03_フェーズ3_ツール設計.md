## 3-1. 解説

### ツール設計がエージェントの性能を決める

フェーズ 2 でツールを定義しましたが、**ツールの「説明文(description)」の質**が、エージェントの賢さを大きく左右します。Anthropic はこれを **ACI(Agent-Computer Interface)**と呼び、「人間向けの UI 設計(HCI)と同じだけの労力を投じるべき」と強調します。

モデルは、ツールの名前と説明文だけを頼りに「どのツールをいつ使うか」を判断します。説明が曖昧なら、モデルは間違ったツールを選んだり、引数を間違えたりします。

### 良いツール設計の原則

**(1) 最小・非重複(minimal, non-overlapping)**
ツールは少なく、役割が重ならないように。Anthropic の名言:

> 「人間のエンジニアが、どのツールを使うべきか即答できないなら、AI エージェントにそれ以上を期待してはいけない。」

`search` と `find` と `query` のような似たツールが並んでいると、モデルは迷います。

**(2) 明確な命名・充実した説明**
ツール名は動詞 + 目的語で具体的に(`get_weather` は良いが `data` は悪い)。説明には「何をするか・いつ使うか・引数の意味・返り値の形・エッジケース」を書きます。

**(3) 名前空間(namespacing)**
ツールが多いときは接頭辞でグループ化します。サービス別なら `asana_search` / `jira_search`、リソース別なら `asana_projects_search` / `asana_users_search`。境界が明確になり、モデルが選びやすくなります。

**(4) コンテキストを節約する出力設計**
ツールの返り値が巨大だと、コンテキストウィンドウを圧迫します(フェーズ 4 の context rot に直結)。全件返すより、要約・ページング・「識別子だけ返して必要時に詳細取得」が有効です。

**(5) 組み合わせ可能(composable)**
1 つのツールは小さく、多様なワークフローで部品として組み合わさるように設計します。

### 落とし穴

- **ツールの数を増やしすぎる**:重複・過多なツールはモデルを混乱させ、非効率な戦略に誘導します。
- **抽象化しすぎ**:凝った高レベルツールより、`bash` や `read_file` のような基本部品の方が、モデルが柔軟に問題を解けることも多い(LangChain も「計算環境を渡してモデルに解法を設計させる」方が良い場合があると指摘)。

## 3-2. 例コード ── 悪いツールと良いツール

```python
# ❌ 悪い例:説明が曖昧、役割が重複、引数の意味が不明
BAD_TOOLS = [
    {"name": "data", "description": "データを扱う",
     "input_schema": {"type": "object", "properties": {"x": {"type": "string"}}}},
    {"name": "get", "description": "取得する",
     "input_schema": {"type": "object", "properties": {"x": {"type": "string"}}}},
]
# → モデルは「data と get のどちらを使うべきか」を判断できない。

# ✅ 良い例:命名が具体的、説明が充実、名前空間で整理
GOOD_TOOLS = [
    {
        "name": "db_users_search",
        "description": (
            "ユーザDBを名前またはメールで検索し、最大20件を返す。"
            "完全一致ではなく部分一致。該当なしの場合は空リストを返す。"
            "個別ユーザの詳細が必要なときは db_users_get を使うこと。"
        ),
        "input_schema": {
            "type": "object",
            "properties": {
                "keyword": {"type": "string", "description": "氏名またはメールの部分文字列"},
                "limit": {"type": "integer", "description": "最大件数(既定20、上限100)"},
            },
            "required": ["keyword"],
        },
    },
    {
        "name": "db_users_get",
        "description": "ユーザIDを指定して、そのユーザ1件の全項目を返す。存在しなければエラー文字列。",
        "input_schema": {
            "type": "object",
            "properties": {"user_id": {"type": "string", "description": "ユーザの一意ID"}},
            "required": ["user_id"],
        },
    },
]
# → search(複数・部分一致)と get(単一・ID指定)の役割が明確に分離。
#   名前空間 db_users_* で境界も明確。
```

### コンテキスト節約の例(識別子だけ返す)

```python
def db_users_search(keyword, limit=20):
    rows = query_db(keyword, limit)
    # ❌ 全項目を返すとコンテキストを圧迫
    # return json.dumps(rows)  # 各ユーザに住所・履歴…と巨大

    # ✅ 一覧では「ID + 名前」だけ返し、詳細は get で都度取得させる(JIT retrieval)
    return json.dumps([{"id": r["id"], "name": r["name"]} for r in rows])
```

## 3-3. 課題

1. **【基礎】** フェーズ 2 の `calculator` ツールの説明文を、わざと "計算する" だけの曖昧な 1 語に変えて、複雑な式での挙動が変わるか観察せよ。次に、対応する演算子と例を説明に足して改善せよ。
2. **【設計】** 「社内ファイル検索エージェント」のツールセットを 3〜4 個設計せよ。`files_search`(キーワードで一覧)、`files_read`(パス指定で全文)など、名前空間と役割分離を意識し、各ツールの説明文をフル(何を・いつ・引数・返り値・エッジケース)で書け。
3. **【批評】** 次のツールセットの問題点を 3 つ指摘し、改善せよ:`search`, `find`, `lookup`, `query`, `get_data`, `fetch`(すべて「データを探す」系で説明が 1 語)。
4. **【発展】** ツールの返り値が 10,000 行ある状況を想定し、コンテキストを圧迫しない返し方を 3 つ考えよ(ページング / 要約 / 識別子のみ返却など)。それぞれの利点・欠点を述べよ。
