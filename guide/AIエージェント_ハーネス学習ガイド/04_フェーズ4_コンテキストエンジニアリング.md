## 4-1. 解説

### コンテキストエンジニアリングとは

> **モデルが受け取る情報を「何を・どう構造化し・いつ context window に入れるか」を設計する規律。**

プロンプトだけでなく、メモリ・ツール・検索・状態を含む「情報環境全体」を設計します。業界では「**2026 年を定義するスキル**」と言われます。モデルがいくら賢くても、見せる情報が不適切なら正しく動けないからです。

### 中心課題:Context Rot(コンテキストの腐敗)

最重要概念です。**コンテキストウィンドウが長くなるほど、最先端モデルでも性能が劣化する**現象を context rot と呼びます。

なぜ起きるか:
- Transformer は全トークン間に n²(総当たり)の関係を計算します。トークンが増えるほど、この「注意(attention)」が薄く引き伸ばされます。
- モデルは超長系列での学習が相対的に少なく、遠く離れた依存関係を扱う力が落ちます。

結論として、モデルにも**有限の「注意予算(attention budget)」**があります。人間のワーキングメモリと同じで、情報を詰め込みすぎると、かえって肝心な点を見失います。

### 核心原則

> **最小で高シグナルなトークンの集合を維持せよ。** コンテキストはモデルが進化しても希少な有限資源として扱う。

「念のため全部入れておく」は最悪手です。ノイズがシグナルを薄めます。

### 4 つの実践テクニック

**(1) Just-In-Time Retrieval(都度取得)**
全データを事前に詰め込まず、軽量な「識別子(ファイルパス・ID)」だけを持たせ、必要になった時点でツールで動的に取得させます。人間がファイル名のメモだけ持ち、必要なときにファイルを開くのと同じ。
→ このプロジェクトの「タスク種別を判定してから、必要な L1/L2/L3 規約だけ Read する」設計がまさにこれ。

**(2) Compaction(圧縮)**
会話履歴が長くなったら要約します。重要な設計判断・未解決の課題は残し、冗長なツール出力は捨てる。コツは「**まず recall(取りこぼさない)を最大化 → 次に precision(無駄を削る)を上げる**」順序。

**(3) Structured Note-Taking(構造化メモ)**
エージェントが外部のメモリファイルに、進捗・決定事項・TODO を書き出します。コンテキストがリセットされても、このファイルを読み直せば一貫性を保てる。長期タスクに必須。
→ このプロジェクトの `memory/` + `MEMORY.md` がこれ。

**(4) Sub-Agent(サブエージェント)**
焦点を絞ったタスクを専門の子エージェントに委譲し、**詳細ではなく要約だけを返させる**。親のコンテキストを軽く保て、複数の子を並列に走らせて探索もできる。
→ このセッションの Agent ツール / Workflow ツールがこれ。

### システムプロンプトとサンプルの "Goldilocks zone"

- **システムプロンプト**:ガチガチのハードコード(脆い)と、曖昧な指示(機能しない)の中間を狙う。「行動を導くほど具体的、かつ強いヒューリスティックを与えるほど柔軟」な"高さ(altitude)"で書く。
- **例(few-shot)**:エッジケースを網羅列挙するより、**多様で代表的(canonical)な例を厳選**する。「LLM にとって、例は千の言葉に値する絵」。

## 4-2. 例コード ── 簡易 Compaction を ReAct ループに足す

フェーズ 2 のループに、「履歴が長くなったら古い部分を要約する」処理を加えます。

```python
def compact_history(messages, client):
    """古い履歴を要約して1メッセージに畳む(簡易版 compaction)"""
    # 直近2ターンは残し、それ以前を要約対象にする
    keep = messages[-2:]
    to_summarize = messages[:-2]
    if len(to_summarize) < 4:        # 十分短ければ圧縮しない
        return messages

    summary_resp = client.messages.create(
        model="claude-haiku-4-5-20251001",   # 要約は軽量モデルで十分・安価
        max_tokens=1024,
        messages=[{
            "role": "user",
            "content": (
                "次のエージェント作業ログを要約せよ。"
                "重要な決定事項・判明した事実・未解決の課題は必ず残し、"
                "冗長なツール出力は捨てること。\n\n"
                + str(to_summarize)
            ),
        }],
    )
    summary = summary_resp.content[0].text
    # 要約1件 + 直近2ターン に畳む
    return [{"role": "user", "content": f"【これまでの要約】\n{summary}"}] + keep


def run_agent_with_compaction(user_message, max_iterations=20, token_budget=8000):
```

## 4-3. 課題

1. **【理解】** context rot を自分の言葉で説明せよ。「コンテキストは長いほど良い」がなぜ誤りか、attention budget の観点から述べよ。
2. **【実装】** 上の `run_agent_with_compaction` を完成させ(フェーズ 2 のツール実行部を埋める)、長い会話で圧縮が走る様子を観察せよ。圧縮前後で会話履歴の長さがどう変わるか比較せよ。
3. **【設計】** あなたが「100 ファイルのコードベースを調査するエージェント」を作るとする。全ファイルを事前に context へ入れる方式と、JIT retrieval 方式のそれぞれについて、トークン消費・精度・レイテンシのトレードオフを表にまとめよ。
4. **【プロジェクト連動】** このリポジトリの `CLAUDE.md` の「Step 1〜4(タスク種別判定 → 必要な規約だけ Read)」が、4 テクニックのどれに当たるか特定し、なぜその設計が context rot を防ぐのか説明せよ。
5. **【発展】** Structured Note-Taking を実装せよ。エージェントに `update_notes(text)` ツールを与え、各ステップで進捗をファイルに書かせる。次にコンテキストをわざとリセット(messages を空に)し、notes ファイルだけ読み直して作業を継続できるか試せ。
