# フェーズ 5:ハーネスの 9 大構成要素 ── 解剖図

> [← 04 コンテキストエンジニアリング](04_フェーズ4_コンテキストエンジニアリング.md) ｜ [06 ワークフロー vs エージェント →](06_フェーズ6_ワークフローvsエージェント.md)

## 5-1. 解説

ここまでで「ループ・ツール・コンテキスト」を学びました。フェーズ 5 では、production レベルのハーネスが持つ**全構成要素を俯瞰**します。あらゆる本格的なハーネスは、次の 9 要素を含みます。

| # | 構成要素 | 役割 | これまでのフェーズとの対応 |
|---|---|---|---|
| 1 | **Model Interface(モデル接続層)** | LLM との対話を抽象化。モデルを差し替え可能にし、system prompt・tool 定義・メッセージ整形・構造化出力パースを担う | フェーズ 1・2 の `client.messages.create` 周辺 |
| 2 | **Tool Registry(ツール登録簿)** | 使えるツールのカタログ(説明・スキーマ・実行ロジック) | フェーズ 3 の `TOOLS` と `run_tool` |
| 3 | **Context Manager(コンテキスト管理)** | 有限の窓を truncation / compression / retrieval / 選択注入で管理。**エージェント失敗の最も一般的な原因がここ** | フェーズ 4 |
| 4 | **Planning Module(計画モジュール)** | 推論方針を決める。Reactive(逐次)/ Planning(先に分解)/ Hierarchical(両者) | フェーズ 2 の ReAct = reactive |
| 5 | **Execution Engine(実行エンジン)** | ツール実行。sandbox・timeout・出力整形・並列を扱う | フェーズ 2 の `run_tool` の拡張 |
| 6 | **Memory System(メモリ)** | 4 種:in-context / external(DB・ベクトル)/ episodic(行動ログ)/ semantic(事実・要約) | フェーズ 4 の note-taking |
| 7 | **Feedback & Observation Loop(観察ループ)** | ツール出力・エラーを捕捉しモデルに返す。「良い観察ループがないとエージェントは盲目で走る」 | フェーズ 2 の tool_result |
| 8 | **Safety & Guardrails(安全層)** | 承認ゲート・危険操作検出・スコープ制限・レート制限・監査ログ | フェーズ 2 の iteration cap、フェーズ 7 |
| 9 | **Orchestration Layer(オーケストレーション)** | マルチエージェント協調(タスクルーティング・spawn・結果集約・状態同期) | フェーズ 6・10 |

### 各要素の補足

**Model Interface(差し替え可能性)**:良いハーネスは、Claude / GPT / Gemini をツールロジックを書き換えずに入れ替えられます。だから「モデル名」を 1 箇所の設定にまとめます。

**Planning Module の 3 種**:
- *Reactive*:1 手ずつ観察して進む(Claude Code はこちら寄り)。柔軟だが先読みは弱い。
- *Planning*:最初に全体計画を立ててから実行。長期タスクに強いが、計画が外れると脆い。
- *Hierarchical*:上位で計画、下位で reactive 実行。両者の折衷。

**Memory の 4 種**:
- *in-context*:今の会話ウィンドウ(最も基本、多くのシステムはこれ中心)。
- *external*:DB やベクトルストア(RAG)。大量知識の保管。
- *episodic*:過去の行動ログ(「前回こう失敗した」)。
- *semantic*:抽出した事実・要約(「ユーザはVBが専門」)。
→ このプロジェクトの `memory/` の `user` / `feedback` / `project` / `reference` 分類は、まさに semantic memory の構造化です。

### ハーネスの土台インフラ(LangChain)

production ハーネスは、上の 9 要素を次のインフラの上に載せます。

- **ファイルシステム**:セッションを跨ぐ永続ストレージ、窓を超えた context 退避、ファイル共有での協調。
- **Git**:進捗追跡と per-step undo(ロールバック)。
- **Bash / コード実行**:あらゆるツールを事前に作るより、計算環境を渡してモデルに解法を設計させる。
- **Sandbox**:生成コードの隔離実行。ランタイム・ブラウザ・テストランナーを備え、エージェントが自分の作業を検証できる。

### 実物の設計思想の違い

| ツール | 設計思想 |
|---|---|
| **Claude Code** | 透明性重視。明示的承認ゲート、厳選ツール、詳細ログ。reactive な ReAct |
| **OpenAI Codex** | ハーネス要素をモデル API 内に密統合。サーバ側ツール管理・統一スレッド |
| **Cursor** | IDE 統合。高度なコードインデックスで context 取得、diff レビューで暗黙承認 |

## 5-2. 例コード ── 9 要素を意識した構造化

これまでバラバラだったコードを、構造体として整理してみます(各要素がどこに対応するかを明示)。

```python
class AgentHarness:
    def __init__(self):
        self.model = "claude-opus-4-8"        # ① Model Interface
        self.tools = TOOLS                     # ② Tool Registry(定義)
        self.tool_impls = {                    # ② + ⑤ Execution Engine
            "calculator": run_calculator,
            "read_file": run_read_file,
        }
        self.messages = []                     # ③ Context Manager / ⑥ in-context memory
        self.max_iterations = 20               # ⑧ Safety: iteration cap
        self.client = anthropic.Anthropic()

    def _compact_if_needed(self):              # ③ Context Manager
        if len(self.messages) > 12:
            self.messages = compact_history(self.messages, self.client)

    def _check_safety(self, name, args):       # ⑧ Safety & Guardrails
        if name == "write_file" and args["path"].startswith("C:/Windows"):
            return False, "システムディレクトリへの書き込みは禁止"
        return True, ""

    def _execute(self, name, args):            # ⑤ Execution Engine + ⑦ Observation
        ok, reason = self._check_safety(name, args)
        if not ok:
            return f"⛔ 拒否: {reason}"        # 安全層がブロック → 観察として返す
        try:
            return self.tool_impls[name](args)
        except Exception as e:
            return f"エラー: {e}"              # ⑦ エラーも Observation

    def run(self, user_message):               # ④ Planning(reactive)+ ループ
        self.messages.append({"role": "user", "content": user_message})
        for i in range(self.max_iterations):
            self._compact_if_needed()
            resp = self.client.messages.create(
                model=self.model, max_tokens=2048,
                tools=self.tools, messages=self.messages,
            )
            self.messages.append({"role": "assistant", "content": resp.content})
            if resp.stop_reason != "tool_use":
                return "".join(b.text for b in resp.content if b.type == "text")
            results = []
            for b in resp.content:
                if b.type == "tool_use":
                    out = self._execute(b.name, b.input)
                    results.append({"type": "tool_result",
                                    "tool_use_id": b.id, "content": out})
            self.messages.append({"role": "user", "content": results})
        return "⚠️ 反復上限"
```

## 5-3. 課題

1. **【俯瞰】** 上の `AgentHarness` クラスの各メソッド/属性が、9 要素のどれに対応するか、コメントを頼りに全部対応づけよ。欠けている要素(⑨ Orchestration など)はどれか指摘せよ。
2. **【実装】** `_check_safety` を拡張し、「`read_file` で `.env` や `secret` を含むパスを読もうとしたら拒否」するガードレールを足せ。拒否理由が Observation としてモデルに返り、モデルが別の手を取る様子を観察せよ。
3. **【設計】** Planning の 3 種(reactive / planning / hierarchical)を、それぞれどんなタスクに向くか具体例とともに述べよ。「10 個のファイルを順に修正する」タスクはどれが向くか、理由とともに。
4. **【プロジェクト連動】** このプロジェクトの構成要素を 9 要素表に当てはめよ。例:Tool Registry = ?、Context Manager = ?、Memory = ?、Safety = ?、Orchestration = ?(ヒント:Skill 群、`memory/`、絶対禁止トップ 10、Workflow ツール)。
5. **【発展】** Git をハーネスのインフラとして使う設計を考えよ。エージェントが各ステップでコミットし、失敗したら直前のコミットに戻す(per-step undo)仕組みの擬似コードを書け。
