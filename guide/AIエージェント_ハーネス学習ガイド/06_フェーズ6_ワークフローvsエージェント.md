## 6-1. 解説

### 最重要の区別:ワークフロー と エージェント

Anthropic は agentic system を 2 種に分けます。

| | 定義 | 制御の主体 |
|---|---|---|
| **Workflow(ワークフロー)** | LLM とツールが **事前定義されたコードパス**で編成される | 開発者(コード) |
| **Agent(エージェント)** | LLM が **自分でプロセスとツール使用を動的に決める** | モデル |

ワークフローは「決まった手順を確実にこなす」、エージェントは「予測不能な問題に柔軟に対応する」。どちらが優れているという話ではなく、**問題に合わせて選ぶ**ものです。

### 鉄則:まずシンプルに

> **最もシンプルな解から始め、必要なときだけ複雑さを足す。**

エージェント化(自律ループ)は、レイテンシとコストを「性能」と引き換えにします。単純なワークフローや 1 回の API 呼び出しで足りるなら、それで十分。**「エージェントにしたいから」ではなく「単純な手法が明確に劣るから」**複雑にするのが正しい順序です。

### 5 つのワークフローパターン

すべての複雑なシステムは、この 5 パターンの組み合わせで説明できます。

**1. Prompt Chaining(連鎖)**
タスクを逐次ステップに分解し、各 LLM 呼び出しが前の出力を処理する。固定的に分解できるタスク向け。
*例*:マーケ文案を作る → それを別言語に翻訳する。

**2. Routing(振り分け)**
入力を分類し、専門の下流処理へ振り分ける。カテゴリごとに別プロンプト・別ツールが有効なとき。
*例*:カスタマーサポートで「返品」「技術質問」「請求」を別ハンドラへ。

**3. Parallelization(並列化)**
- *sectioning*:独立したサブ作業を分割して同時実行。
- *voting*:同じ問題を複数回試して多数決で確信度を上げる。
*例*:ガードレール(本処理と安全チェックを並列)、コードレビューの多視点。

**4. Orchestrator-Workers(編成役 + 作業役)**
中央 LLM が、**事前には予測できない**サブタスクに動的分解し、専門 worker に委譲して結果を集約。
*例*:複数ファイルにまたがるコード変更(どのファイルを直すかは実行時にしかわからない)。

**5. Evaluator-Optimizer(評価役 + 最適化役)**
一方の LLM が生成し、もう一方が評価・フィードバックする。これをループ。明確な評価基準があり、反復改善が測定可能な価値を生むときに有効。
*例*:翻訳を生成 → 評価役が「ここが不自然」と指摘 → 修正、を繰り返す。

> マルチエージェント(複数の自律エージェントの協調)は、これらを発展させたものです。本格的なパターン(Supervisor / A2A / handoff など)は **フェーズ 10** で扱います。

### エージェント成功の 3 原則

1. **Simplicity(単純さ)**:不要な複雑さを入れない。
2. **Transparency(透明性)**:計画ステップを明示的に見せる(ユーザが何が起きるか分かる)。
3. **ツール文書化・テスト**:ACI に HCI 同等の労力を投じる(フェーズ 3)。

## 6-2. 例コード ── 各パターンの最小実装

```python
# ask() は「1回の素のモデル呼び出しでテキストを返す」ヘルパとする
def ask(prompt):
    r = client.messages.create(model="claude-opus-4-8", max_tokens=1024,
                               messages=[{"role": "user", "content": prompt}])
    return r.content[0].text

# ── 1. Prompt Chaining(連鎖)──
def chain(topic):
    draft = ask(f"{topic} について 3 文の宣伝コピーを書け")        # ステップ1
    polished = ask(f"次のコピーを英語に翻訳せよ:\n{draft}")        # ステップ2(前の出力を使う)
    return polished

# ── 2. Routing(振り分け)──
def route(query):
    category = ask(f"次を「返品/技術/請求」で分類。単語のみ:\n{query}")
    handlers = {"返品": handle_return, "技術": handle_tech, "請求": handle_billing}
    return handlers.get(category.strip(), handle_default)(query)

# ── 3. Parallelization / voting(多数決)──
from concurrent.futures import ThreadPoolExecutor
def vote(question, n=3):
    with ThreadPoolExecutor() as ex:
        answers = list(ex.map(lambda _: ask(question), range(n)))
    # 最頻の回答を採用(簡易)
    return max(set(answers), key=answers.count)

# ── 4. Orchestrator-Workers(編成役+作業役)──
import json
def orchestrate(task):
    subtasks = ask(f"次のタスクを独立したサブタスクのリスト(JSON配列)に分解:\n{task}")
    subtasks = json.loads(subtasks)
    with ThreadPoolExecutor() as ex:
        results = list(ex.map(lambda st: ask(f"次を実行:{st}"), subtasks))  # worker
    return ask(f"次の部分結果を統合して最終成果物に:\n{results}")            # 集約

# ── 5. Evaluator-Optimizer(評価役+最適化役)──
def evaluate_optimize(task, max_rounds=3):
    result = ask(f"次を実行:{task}")
    for _ in range(max_rounds):
        critique = ask(f"次の成果物を評価し、問題点があれば列挙、なければ 'OK':\n{result}")
        if "OK" in critique[:5]:
            break
        result = ask(f"次の指摘を踏まえて改善せよ:\n成果物:{result}\n指摘:{critique}")
    return result
```

## 6-3. 課題

1. **【判断】** 次の各タスクに、5 パターン(または「単純な 1 回呼び出し」「自律エージェント」)のどれが最適か選び、理由を述べよ:(a) ユーザの問い合わせを部署に振り分ける (b) 長文を要約して翻訳する (c) 未知のバグを調査して複数ファイルを修正する (d) 生成した文章の品質を高める。
2. **【実装】** 上の `evaluate_optimize` を実際に動かし、「短編詩を書く」タスクで評価役が何回ダメ出しするか観察せよ。`max_rounds` を変えて品質との関係を見よ。
3. **【実装】** `vote`(多数決)で、曖昧な質問(例:「1+1 は?ただし 2 進数で」)を投げ、回答がばらつく様子と多数決の効果を観察せよ。
4. **【設計】** 「リポジトリ全体のセキュリティ監査」をマルチエージェントで設計せよ。どこを並列化し(parallel)、どこを連鎖させ(pipeline)、どこで結果を集約するか、依存グラフを図示せよ。
5. **【プロジェクト連動】** このセッションの Workflow ツールの `pipeline()` と `parallel()` が、5 パターンのどれに対応するか説明せよ。なぜ `parallel()` は「barrier(全部待つ)」で `pipeline()` は「barrier なし」なのか、性能の観点から述べよ。
